# 日报按公开公告批次处理

日报不再把“今天已发送过任何论文”当作停止条件，不按北京时间昨日提交日期切片。

1. 邮件和飞书均读取八类 arXiv Atom RSS：cs.CV、cs.RO、cs.GR、cs.AI、cs.LG、astro-ph.EP、astro-ph.IM、eess.IV。保留 new/cross，排除 replacement；entry.published 是公告批次日期标签，不是提交日期；feed.updated 只是生成时间。
2. 两边采用相同的方向覆盖召回，每批最多 100 篇候选，不再把邮件 RSS 的前 100 条误当作最相关候选。排序均使用最近30天70%＋全库30%的加权摘要余弦相似度（近期半衰期14天），再做有真实 Zotero 引用的任务/方法审查。邮件分数是飞书的10倍，排序尺度等价。最多30篇；不足5篇正式相关时只补明确标注的待核验候选，不把弱相关冒充正式推荐，也不凭空生成论文。两边已发历史不同，排重后的候选仍可能不同。
3. 在 recommendation-state 分支持久保存公共元数据快照与 announcement-ledger.json 索引。发送失败的已观察批次留在队列，后续运行优先处理最早未完成批次。
4. 只有 SMTP 接受或飞书全部分片 API 接受后才标记完成。正常新批次按去版本号 arXiv ID 的摘要哈希，排除已确认的正式推荐；待核验不计入正式已发。日报与周期补选共享同一投递并发组，避免同时发送造成去重竞态。历史复盘允许有标注地再次查看已读批次。策略/分类升级不会重发已完成公告日，但可保存更新后的候选用于以后复盘。
5. 没有待发新批次时，08:00—20:00静默；20:00后对未得到内容的服务日提供最近14天缓存批次的5篇历史复盘。若任务延迟至次日00:00—08:00，继续补偿前一天服务日，回执和正文保留该日期。服务日已有新批次或周期补选时不再额外复盘。GitHub全天未运行、无缓存或网络故障仍不能保证有内容，不伪造成功。
6. 每次只处理一个待发批次，后续日内尝试继续消化积压。邮件 09:23、13:23、17:23、21:23；飞书 09:17、13:17、17:17、21:17（北京时间）。GitHub 定时是尽力调度，仍可能延迟或丢失。

边界：队列可以恢复已经成功抓取并持久保存、但没有完成发送的批次。若 GitHub 完全没有运行，导致一个 RSS 窗口从未被观察，RSS 本身不能重新提供那个历史批次；现有周/月/年全时间窗口补选负责覆盖这些文献，不能把提交日期伪称为原始公告日期。旧的无批次回执不会凭空认定为新格式完成状态。

公开状态分支只存公共 arXiv 元数据和投递状态，不存密钥、邮箱地址、飞书群 ID 或 Zotero 文献库内容。周期补选 ledger 与日报公告 ledger 是不同文件，CAS 更新避免覆盖冲突。

这套v2策略有意改变了邮件原版的全库rank-log权重及RSS顺序召回，不再宣称与官方原版完全一致。标题、摘要输入统一空白规范化并截取8000字符；保存时间相同的参考文献按key确定顺序。method必须给出具体源机制、目标模块及可在候选摘要核对的原文证据；三维重建不要求额外具备导航应用。邮件展示中文简介、画像关联依据和诊断状态；中文生成失败重试后仍失败则不发送英文摘要兜底。公开邮件诊断预览会移除具体Zotero引用，仅真实邮件包含这些私人关联信息。
