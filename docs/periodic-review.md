# 周、月、年补选方案与使用

## 不改变日报
日报继续最多100篇候选、最多30篇输出。原有邮件/飞书日报排序保持不变。
新增独立的 `Periodic Paper Review` GitHub Actions 工作流，不需要本地服务。

## 何时补选
按北京时间完整日历周期：
- 周一触发上周一00:00至本周一00:00。
- 每月1日触发上月1日00:00至本月1日00:00。
- 每年1月1日触发上一自然年。
同日多个周期分别处理，不覆盖日报或彼此去重凭据。
工作流每天分散尝试4次；错过首次运行、接口错误或长任务中断会续跑尚未完成的周期。
初次启用从启用日开始排期，不自动启动部署日前的全年巨量扫描。
可以在 Actions 手动选择 `week/month/year`，`end` 是排他终点：
周必须周一、月必须1日、年必须1月1日；留空默认最近已完成周期。
`verify_only=true` 生成报告，不发送，不写完成记录。

## 扫描范围与时间口径
八类：cs.CV、cs.RO、cs.GR、cs.AI、cs.LG、astro-ph.EP、astro-ph.IM、eess.IV，包含跨分类。
通过 arXiv 官方 API 的 `submittedDate`（GMT分钟范围）查询，并按 `published`
精确过滤北京时间半开区间。这里是首次提交时间，不是公告日期或最近修订时间。
因此与日报RSS公告列表不是同一个日期口径。
扫描的是检索时 arXiv 已公开可检索的记录，不保证尚未公告/尚未索引的稿件已可见。
周末稿件迟到仍可在后续月/年补选再次检索。

每个周期按日分片，全分页，跨分类/版本按arXiv ID去重；不以100截断。
totalResults缺失、分页提前空、条目重复/损坏、页间总数变化均视为失败，不能假报0篇。
遵循单连接、请求至少3.2秒间隔；不要手动并行启动两个仓库的历史检索。
参考：[官方API手册](https://info.arxiv.org/help/api/user-manual.html)、
[官方使用限制](https://info.arxiv.org/help/api/tou.html)。

## 最新兴趣与筛选
每个周期开始筛选时重新读取完整Zotero，分页过程中版本变化即失败重试。
参考文献与日报采用相同的三种类型、标题/摘要非空、DOI/arXiv/标题去重。
使用在线BAAI/bge-m3的摘要向量；全周期每个未排除候选都参与相似度计算：
1. 全库以保存顺序的log权重归一化；
2. 最近30天再加14天半衰期权重；
3. 30%全库 + 70%近期分布；没有近期记录退回全库；
4. 加权余弦×10排序（不是概率；不对质心再次归一化）；
5. 依次审查排序批次，直到找到30篇具体任务/方法相关论文，或耗尽候选。
不局限前100或固定前若干篇审查，不用泛词匹配凑数。
邮件和飞书的**周期补选**使用完全一致的代码和近期权重；这不意味着两边原有日报策略已相同。

排除Zotero已保存文献（即使该记录没摘要）、已正式推送文献及显式排除ID。
日报的待核验/diagnostic不算已正式推荐，以后可补选。
每个周期最多30篇，允许少于5篇/0篇；补选不强制凑5。
引用实际Zotero参考文献解释原因，中文TLDR，首次提交日期，相似度，论文页/PDF链接。
如要排除指定ID，在仓库变量 `PERIODIC_EXCLUDE_IDS` 填逗号分隔的arXiv ID。
目前云端不会自动读取机器人对话中的“none”反馈，不能声称对话反馈已接入此排除表。

## 持久化、重试和隐私
独立 `recommendation-state` 分支存 `periodic-ledger.json`：
启用日期、已完成周期、成功发送时间、正式推荐ID的SHA256。
不存密钥、收件邮箱、飞书群ID、Zotero标题/摘要/条目key。
日报和周期任务均把真实发送凭据合并到该分支，冲突使用SHA重试合并。
升级时从尚未过期的日报发送凭据导入；过期/不存在的历史凭据无法追溯，
所以不能承诺上线前所有旧推送都可去重。
两仓库分别去重，邮件收到不阻止飞书收到，反之亦然。

发送成功凭据（SMTP接受 / 飞书所有卡片真实message_id）上传为 `periodic-delivery`。
空补选只标记该周期完成，绝不把当日日报标为完成。
凭据先保存，再更新分支；若分支更新失败，后续运行从凭据恢复。
SMTP响应丢失及跨系统故障无法保证严格exactly-once；飞书增加稳定UUID降低重发，
其服务端幂等保留期有限。不能把工作流绿色当作用户已收到/已阅读。

GitHub cache存公共arXiv元数据、BGE向量、不可逆画像摘要关联的审查布尔值；
不缓存Zotero明文或密钥。完全抓完一天才写检查点，模型/摘要变化重算向量。
新画像重新计算分数并使旧审查缓存失效，不复用旧推荐结果。
缓存丢失可重新抓，不丢失独立分支中的已发送记录。
75分钟预算后保存未完成进度，后续尝试续跑，不发送不完整周期列表。
全年量大，会产生明显更多在线嵌入/审查请求和Actions耗时。
这是完整扫描，不是“全年只挑100篇”；可手动dry-run先评估。
受GitHub调度、Actions额度、API额度、网络可用性制约，不承诺绝对准时/必达。

## 如何验证
`periodic-review-report` 包含HTML及JSON：
- period_key、time_basis、metadata_complete；
- 全周期candidate_count、排除后数量、审查数、输出数；
- 本次Zotero版本、数量、读取时间、明确权重参数；
- 按相似度降序的结果及真实参考文献/理由。
查看 `periodic-delivery` 验证实际发送，而非仅看绿色。
`tests/test_periodic_review.py` 可离线验证日历、分页、全年断点、
超100候选排序、新增兴趣改变排序、排除、失败与dry-run不记完成。

两个仓库的 `scripts/periodic_review.py`、`scripts/periodic_relevance.py`
和周期测试保持逐字一致；修改时必须同步，不靠复制旧画像维持一致性。
